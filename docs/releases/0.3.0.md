# KPress 0.3.0

KPress `0.3.0` makes embedded KPress purely declarative, in two coordinated changes
planned in [Declarative Embedding plan](../done/declarative-embedding.plan.md): sizing
derives from one base knob ([issue #37](https://github.com/jlevy/kpress/issues/37)), and
theming reads one resolved attribute at one scope
([issue #38](https://github.com/jlevy/kpress/issues/38)). The pre-release host-safety
follow-up also makes fragment asset ownership explicit
([issue #42](https://github.com/jlevy/kpress/issues/42)).

## Root-Independent Sizing

Every font size — the size-token ramp, all headings, code, labels, the bullet glyph, and
its offsets — now derives from a single public knob, `--kpress-font-size-base` (default
`1rem`), as `calc(base × ratio)`. No internal font-size rule references `rem`
(lint-enforced), so an embedded document’s proportions no longer depend on the host
page’s root font size.

- **Standalone pages are unchanged**: the `1rem` default still resolves against the
  reader’s browser preference.
- **Embedders** set `--kpress-host-font-size-base: 17px` (or any length) once on
  `:root`; the whole document scales as one unit, including body-appended tooltips.
  Migration: hosts that previously overrode `--kpress-font-size-normal` (or restated
  ratios in `em`) should delete those overrides and set the base instead — `normal` and
  the rest of the ramp are now derived from the base.
- **Print output changes deliberately**: the print stylesheet re-roots the base at
  `--kpress-print-font-size`, so paper output now keeps the designed ratios (previously
  an 11pt-pinned body printed against 16px-rooted headings, rendering h1/body at ~1.85
  instead of the designed 1.7).
- Layout lengths (the `48rem` reading measure, container-query bands, tooltip width
  caps, page margins) stay deliberately root-relative; see
  [Sizing Policy](../kpress-design.md#sizing-policy).

A two-root real-browser regression test asserts both halves of the contract (including a
body-portaled overlay): pinned base ⇒ identical computed sizes across root font sizes;
default base ⇒ proportional scaling with the design ratios intact.

The derived tier is public: the full size ramp, the h2–h4 heading tokens,
`--kpress-caps-label-size`, and `--kpress-bullet-size` join the reader and fragment
contracts as the sanctioned seam for deliberate design divergence (a host aligning mono
or label sizes with its own chrome).
Scale through the base; override a ramp token only to depart from its ratio on purpose.

## Single-Scope Declarative Theming

CSS now reads exactly one theme input, `data-kpress-resolved-theme="light|dark"`, keyed
symmetrically for light and dark at two scopes — any ancestor (`:root` or a plain host
wrapper) and the element itself, element winning — so a stamped element is a coherent
theme island in either direction instead of a specificity accident.
`color-scheme` is declared in rules keyed identically to the palette, so native controls
can never split from the document colors (previously an element-scoped system-theme
embed could get a dark palette with light `color-scheme`). The mode attribute
(`data-kpress-theme`) no longer keys any CSS (lint-enforced), and `theme-light.css` /
`theme-dark.css` folded into `style-tokens.css`.

Fragment SSR is theme-agnostic: rendered fragments bake no theme or palette attributes,
render byte-identically across themes and palettes, and the dynamic render cache shares
one entry across theme states.
Standalone pages are unchanged (`<html>` attributes + pre-paint bootstrap).

## Host-Safe Fragment Assets

Automatic asset selection now respects the page/fragment boundary:

- Standalone pages keep their default settings widget and `theme.js` resolver.
- Fragments default to no widgets and omit `theme.js`; a plain fragment can therefore be
  CSS-only, while rich fragments select only their rendered feature modules.
- `RenderOptions.include_theme_resolver` and
  `KPressRenderRequest.include_theme_resolver` opt a fragment into KPress ownership of
  root theme attributes, the `kpress.theme` storage key, and OS-theme tracking under
  automatic asset selection.
- Explicit fragment settings no longer pull in the resolver.
  Their behavior-neutral controls emit `theme:request`; the owning layer applies state
  and emits `theme:change`. The standalone resolver handles the same event when
  included.

This removes the late-load multiple-writer race: loading every declared fragment entry
point after document ready cannot overwrite a host stamp unless the request explicitly
selected the resolver.
A real-Chromium regression covers the conflicting stored-dark, OS-dark, host-light case
and the explicit opt-in case.

The dynamic request contract makes a corresponding alpha hard cut: the inert
`KPressRenderRequest.theme_mode` and `resolved_theme` fields are removed.
Theme state belongs to the host by default; resolver inclusion is the only per-request
theme choice. The explicit `asset_policy="all"` still means the complete reader bundle,
including the resolver; host-owned fragments use the default `auto` policy or `none`.

## Migration Table

| If your host… | Then in 0.3.0… |
| --- | --- |
| Overrode `--kpress-font-size-normal` or restated kpress ratios in `em` (the metabrowser-style bridge) | Delete the whole bridge; set `--kpress-host-font-size-base` once on `:root`. Keep only overrides that are deliberate design divergence, expressed via the now-public ramp/label/bullet tokens. |
| Suppressed the ≥64rem heading step-up via element-scope size overrides | After deleting the bridge, the wide-pane h2–h4 step-up reappears in embedded panes. Intended; re-pin `--kpress-font-size-h2/h3/h4` only if your design wants the tight scale at every width. |
| Redeclares `--kpress-font-size-base` itself instead of using the hook | Your value also overrides kpress’s print re-rooting; use the hook if print should follow `--kpress-print-font-size`. |
| Read the baked `data-kpress-theme` / `data-kpress-resolved-theme` / `data-kpress-palette` attributes off rendered fragments (including test assertions) | Those attributes are gone from fragments. Stamp `data-kpress-resolved-theme` (and optionally the palette) on your chosen scope and assert against your own stamping. |
| Re-stamped theme attributes onto every rendered `.kpress` element on toggle | One scope suffices now; delete the element-chasing loop. Element-level attributes still work and win (theme islands). |
| Uses a non-`:root` wrapper as the theme/size scope | Body-portaled overlays (tooltips, previews) escape the wrapper; stamp `:root` as well. |
| Constructed `KPressRenderRequest(theme_mode=…, resolved_theme=…)` | Remove both arguments. Stamp the host’s resolved state on its chosen scope; set `include_theme_resolver=True` only when KPress should own resolution. |
| Relied on the fragment’s page-default settings widget | Widgets now default to `{}` for fragments. Request `widgets={"settings": "on"}` explicitly and mount it in host chrome. |
| Uses KPress settings with a host-owned theme | Listen for `theme:request`, apply the requested mode through host policy, and emit `theme:change` with `{mode, resolved}`. After mounting settings, emit that initial change once with the host’s current state. No behavior override or post-load neutralizer is needed. |
| Loads `theme.js` in embeds | Leave `include_theme_resolver=False` so automatic manifests omit it. If KPress should own the embedded surface’s root state, storage, and OS listener, opt in explicitly. |
| Imported `bindThemeToggleControls` from `theme.js` | Import it from `theme-controls.js`. Importing `theme.js` opts into the standalone resolver; the behavior-neutral controls have their own module. |
| Published a fixed `light` or `dark` standalone site with settings off and expected no theme runtime | Standalone pages now include `theme.js` independently of settings and configured color mode. Library callers can pass `RenderOptions(include_theme_resolver=False)` to `render_page` to omit the resolver module; the inline pre-paint bootstrap remains. `kpress.yml` has no page-level resolver opt-out. |
| Still uses pre-alpha `--kpress-host-bg`, `--kpress-host-text`, or related color hooks | Replace them with the public `--kpress-doc-*` color tokens. The host-color aliases were removed before `v0.1.0` and were never part of a tagged `0.2.x` contract, so this corrects an old integration rather than a new 0.3 removal. |
