# KPress 0.3.2

KPress `0.3.2` is a compatible maintenance release for the `0.3` declarative-embedding
line.
It fixes two typographic rules that were evaluated against the wrong scope, so each
was correct in the configuration it was written for and wrong everywhere else.

There is no API change.
No name, CSS class, CSS variable, template variable, or data attribute was added,
removed, or renamed, and no option changed its default.
Both fixes are CSS-only; the rendered HTML is byte-identical apart from the asset hash.

## Table Code Steps Down a Mono Tier at Every Width

The two size ramps in `style-tokens.css` pair by index — `mono`/`normal` at 0.820,
`mono-small`/`smaller` at 0.833, `mono-tiny`/`tiny` at 0.824 — which is what holds code
at one optical weight against whatever text surrounds it.

A table is the one surface that reduces its text (to `small`) while leaving code at
`mono`, putting code at 0.863 of its own cell: heavier inside a table than the identical
span in prose, and mono’s larger x-height exaggerates the gap further.

`.kpress-table code / pre` already selected `mono-small`, but only inside
`@container kpress-doc (max-width: 47.99rem)`. That band looked correct for the wrong
reason — it *also* drops table text to `smaller`, so the pairing was coming from the
text side rather than from this declaration.
Every wider pane fell through to the base `.kpress code` rule.

The declaration is now a base table rule and the band copy is gone.
`small` has no mono partner (the text ramp has four tiers, mono has three), so neither
candidate is exact; `mono-small` lands at 0.789 against `mono`’s 0.863, closer to the
ramp’s 0.82, and reads as subordinate rather than competing.

Measured in Chromium at the 16px default:

| Pane | Cell text | Code before | Code after |
| --- | --- | --- | --- |
| 1300px | 15.2px | 13.12px (0.863) | 12px (0.789) |
| 600px | 14.4px | 12px (0.833) | 12px, unchanged |

The narrow band is untouched, as intended; its text-side rule already produced this
result.

## The Content Card Follows the Pane, Not the Window

The card border and the `4rem` inline padding that makes room for it were the last two
responsive rules in `components.css` still keyed to `@media (min-width: 768px)`, in a
file whose own contract states that everything responsive keys off
`@container kpress-doc` — the width of the scroll pane, **not** the window.

The rule that undoes them is a container query
(`@container kpress-doc (max-width: 47.99rem)`, which supplies a `0.75rem` gutter).
When the pane and the window disagree, so did the two rules: a pane narrower than 48rem
inside a window wider than 768px drew the card border around the phone band’s gutter.
The result was a hairline pressed against the text on both sides and running through the
disclosure chevrons — a card drawn around phone geometry, which is exactly what the
card’s premise rules out, since it is supposed to add chrome to geometry that is already
the card’s.

Both blocks now use `@container kpress-doc (min-width: 48rem)`, the same boundary the
phone band undoes itself at.
The border and the padding that makes room for it arrive together.
No threshold moved: 48rem is the same 768px, measured against the right box.

### What Changes for You

**Embedding hosts** are the main beneficiaries, because a host pane is routinely
narrower than the window.
A pane between roughly 30rem and 48rem previously showed the tight box and now reads
full-bleed, as narrow panes are meant to:

| Pane width | Before | After |
| --- | --- | --- |
| < 30rem | no border, `0.75rem` gutter | unchanged |
| 30–48rem | **border with `0.75rem` gutter** | no border, `0.75rem` gutter |
| ≥ 48rem | border with `4rem` padding | unchanged |

**Standalone pages are also affected**, which is worth stating plainly because the
standalone container is the window *minus* the page gutter
(`--kpress-page-margin-inline`, `2rem` per side above the phone breakpoint).
A standalone page therefore reaches a 48rem container at about an 832px window, not a
768px one.

Between those two widths, `0.3.1` drew the same broken box a host pane did — verified in
Chromium at an 800px window, where the released stylesheet produces `border: 1px solid`
against a 12px gutter.
`0.3.2` renders that band full-bleed instead.

So a standalone page between roughly 768px and 832px of window width loses a border it
used to have. That is the fix rather than a regression: the border it loses is the one
that was pressed against the text.

Wider and narrower standalone windows are unchanged.

## Follow-Up

`docs/kpress-design.md` describes the card as appearing “only at md+ widths” without
saying which box is measured — the ambiguity this bug turned on.
It now says pane width.

## Compatibility

No migration is required, and no configuration needs to change.
A `0.3.1` host that upgrades and changes nothing gets the corrected typography; hosts
that set `format.content_card: false` are unaffected by the card change entirely.

## Verification

The complete Python and JavaScript quality gates, locked-graph dependency audits,
distribution inspection, clean-room wheel install, and the Python 3.12–3.14 CI matrix
run before publication.

Both fixes are geometry claims, so both were measured in a real engine rather than
asserted: container queries and `cqw`-keyed caps are not evaluated by browserless DOM
emulation. The card behavior was probed over the DevTools protocol in an embedding host
at pane widths from 400px to 980px, and standalone at window widths from 760px to 900px
against both the released and the fixed stylesheet.
A contract test pins the table rule at nesting depth zero, so re-scoping it to a band
fails the build rather than regressing quietly.

The exact PyPI artifact is verified separately after trusted publication.
