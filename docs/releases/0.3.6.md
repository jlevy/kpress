# KPress 0.3.6

Code is set in a face KPress ships.
Before this, code was the one role a document drew from whatever mono the reader’s
machine happened to have, so a printed page embedded the exporting machine’s Menlo — 56
KB of it, in the explainer PDF that started this work.

## Planetaire Mono Text

**Planetaire Mono Text** — B612 Mono’s letterforms with Hack’s punctuation and symbols,
under the SIL Open Font License — is vendored as latin subsets and set at `0.82` of the
prose size, a ratio measured against the two faces’ ink rather than picked blind:
Planetaire draws an x-height of 0.560 em against PT Serif’s 0.500, so x-height parity
would want 0.893 and `0.82` lands code at 91.8% of the prose x-height beside it,
deliberately below parity so a code span reads as an inset.

Two settings control it, and both are publishing decisions rather than reader switches:

- `format.mono_font` — `planetaire` (the default) or `system`. `system` hands code back
  to the platform stack **and drops every Planetaire face from the manifest**, so a page
  under it neither fetches nor copies one.
- `format.mono_weights` — which styles the document declares.

## The Default Declares Four Styles, and Narrowing Below Them Is Refused

The default is `regular`, `bold`, `italic` and `bold-italic`: every style KPress’s own
stylesheets ask for.
`code` resolves to 400 and the highlighter’s keywords to 700; `syntax.css` sets comment
tokens italic and preprocessor and docstring tokens italic *and* 700.

Two facts decide that, and they pull the same way.

**Declaring is not loading.** A browser fetches a declared face only when a glyph
resolves to it, so a declaration costs a page nothing until its style appears.
Measured with all four declared: a prose page with no code fetches none of them; a page
of Python fetches three and leaves bold-italic unloaded, because Pygments’ Python lexer
emits no italic-and-700 token.
What the set changes is the **built tree** — the four are copied into a static build and
the other three (48 KB of woff2) are not.

**Synthesis is what breaks the rule that every glyph comes from a shipped face.** A
style a rule asks for and a document withholds is not absent from the page; the browser
invents it. A missing slant is drawn by shearing the upright face — still `/Type0` in a
PDF, but leaning 14.0° against the 11° the face is drawn with.
A missing weight is drawn by emboldening a lighter face, which Chromium emits as
**`/Type3` glyph procedures**: a page of paths that only looks like text, unsearchable
and unselectable, and the precise failure this face was vendored to remove.

So a set that leaves either axis synthesized is now refused at config load, naming the
missing styles and what the browser would have drawn instead.
`[regular, bold]` is refused for the slant; `[regular, bold, italic]`,
`[regular, italic]` and `[regular]` were each measured producing `/Type3`, the last at
2.8× the PDF size. `italic` and `bold-italic` are added and dropped together.
`medium`, `semibold` and `extrabold` stay opt-in — nothing packaged asks for them, so
their absence synthesizes nothing.

**If you set `mono_weights`,** a set narrower than the four now fails the build with a
message naming the fix.
To ship no mono face at all, set `mono_font: system`; an empty weight list is not the
way to say that, and is refused too.

## Also in This Release

- `KPressRenderRequest` and `KPressExportRequest` carry `mono_font` and `mono_weights`,
  so an embed or a single-document export (`--pdf` included) can decline the face the
  way a static publish already could.
- The reader’s system-font toggle keeps honouring `--kpress-host-font-mono`. The mono
  line added to that block set a bare stack, which discarded a host’s chosen face the
  moment a reader flipped system fonts on.
- The `-small` and `-tiny` mono rungs are `0.9` and `0.85` of the mono rung — the prose
  ramp’s own steps, since the two ramps pair by index — so all three rungs hold the same
  91.8%. They were `0.915` and `0.855`, the pre-Planetaire absolutes rescaled, which
  left those two above the rung they sit under.
- `NOTICE.md` and the fonts README record what the shipped bytes say: the vendored
  v0.2.0 faces carry `Version 0.1.5` internally, because upstream built them before it
  tagged the release. Only the version records differ; the outlines and metrics are
  v0.2.0’s. The Eclipse Public License 2.0 and the Nerd Fonts licence now ship beside
  the OFL, so every grant the faces’ own records name travels with them.

## Mathematics Uses the Reading Face

Letters and digits in mathematics are now drawn from the face around them rather than
from Computer Modern: PT Serif in prose, and Source Sans 3 in sans roles such as
captions, footnotes, and table cells.
Two composite families, `KPress Math Text` and `KPress Math Text Sans`, take the Latin
and digit ranges from the reading face and keep KaTeX’s Greek, operators, and
delimiters. `format.math_text_font` controls this: `prose` (the default) or `katex` for
the previous look.

- Math waits for the composite faces before its first render, so digits no longer flash
  from KaTeX’s face into the reading face.
- After rendering, only the faces an expression actually drew are awaited, so a page no
  longer waits on families it never uses.
- Font readiness loads each family in a stack separately, which fixes a WebKit path that
  could report a multi-family load ready before its later families had arrived.
- A host that renders its own mathematics can use `kpressMathText.ready()`, `render()`,
  `hydrate()`, `installTablesFor()`, `restore()`, and `complete()`, pinned in
  `PUBLIC_MATH_RUNTIME_METHODS`. Server-prepared math markup carries the attributes
  pinned in `PUBLIC_MATH_PREPARED_ATTRIBUTES` and is hydrated without a re-render.

## Fonts and Print

- Print and PDF output use static “KPress Print Sans” instances of Source Sans 3, so
  sans headings and the page footer embed as real fonts rather than outline paths.
  The PDF exporter waits for print faces, including `@page` margin-box families, before
  it writes.
- Quotation marks and apostrophes come from a shipped six-glyph face, `KPress Quotes`,
  instead of the reader’s local Georgia, so they match on every machine and embed in
  PDFs. `--kpress-host-font-punctuation` swaps them.
- List markers are a `currentColor` box rather than a font glyph, so they need no
  installed font, embed nothing in a PDF, and stay visible in forced-colors mode and
  right-to-left documents.
- Regular sans text uses `--kpress-font-weight-sans-regular` (410), Source Sans 3’s
  optical regular, in every sans context including math and print.
- `--kpress-host-font-size-mono` lets a host that swaps the mono face retune the mono
  size rung; the small and tiny mono rungs derive from it.
- Footnotes sit on the `--kpress-font-size-small` rung, and the page shell drops its top
  padding in print, as it already did its side gutters.

## Reader Behavior

- Reader panes restore their scroll position after a reload and after a back/forward
  cache `pageshow`. Hosts that scroll the document keep the browser’s native
  restoration.
- Footnote and section tooltips have a close button.
  Escape closes a tooltip and returns focus to its anchor; a click or tap outside closes
  it; Tab from the anchor reaches the close button; re-tapping an anchor on touch
  toggles it. A tooltip that holds keyboard focus stays open when the pointer leaves.
- Switching the reading face between serif and sans reloads a page that contains math,
  because the math metric tables are fixed at load.
  Pages without math still switch in place.

## Security and Dependency Updates

- The optimizer tool’s lockfile, which ships in the wheel and is installed when a
  publish runs the optimizer, moves `svgo` to 4.1.0 and `source-map-js` to 1.2.2. The
  latter fixes GHSA-68fv-2mgg-jv7q, a denial of service from crafted indexed source
  maps.
- The `optimize` extra still accepts `brotli>=1.2.0`, but every release through 1.2.0
  carries CVE-2026-111497, an out-of-bounds write in the Brotli decoder.
  KPress only compresses with it; install `brotli` 1.2.1 or newer anyway, since other
  libraries decode Brotli data whenever it is installed.
- Development tooling moves to Vitest 5.0.3 for GHSA-qxg6-89mg-rqv8 and
  GHSA-xp26-3454-mjgp, which also brings Vite 8.3.4. None of this ships in the wheel.

## For Host Integrators

- The public contract adds `--kpress-font-weight-sans-regular`;
  `--kpress-host-font-punctuation`, `--kpress-host-font-sans-print`, and
  `--kpress-host-font-size-mono`; the `math_text_font` and `mono_font` template
  variables; `MathTextFont`, `MonoFont`, and `MonoWeight`; and the two math runtime
  tuples above. Nothing was removed.
- Math reads no host font hook: a host that replaces the reading face through
  `--kpress-host-font-prose` keeps KPress’s faces in mathematics until it declares its
  own `KPress Math Text` faces, or opts out with `data-kpress-math-text="katex"` on its
  root. See “Math Text Face” in `kpress-design.md`.
- `mono_weights` is validated on `RenderOptions` as well as at config load, so a Python
  host that passes a set the browser would have to synthesize now gets
  `KPressInvalidRequestError`.
- A host that styles list markers itself must set `content` and clear `background`,
  because the default marker is now a box rather than a glyph.

## Verification

The usual gates and the 3.12–3.14 matrix run before publication.

The two real-browser mono files now run in the job that installs pinned Chromium, rather
than falling through to the runner’s own Chrome.
`subset_mono --check` prints which of its two modes it ran — the fresh-subset rebuild or
the weaker pinned-hash comparison — and refuses a partly populated font cache instead of
downgrading to the weak one, and CI fetches the pinned upstream faces so the strong
check actually runs there.
The PDF regression asserts every embedded face is one KPress ships, rather than
denylisting the two a macOS developer would see.
