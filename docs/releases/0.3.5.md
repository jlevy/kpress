# KPress 0.3.5

KPress `0.3.5` fixes a regression introduced in `0.3.4`. The wide band’s column inset
became conditional on whether a table of contents was rendered, so a wide document
without one drew its content card with different inner padding than the same document
with one.

Nothing else changes.
No public name, class, variable, template variable, or data attribute moves.

## The Wide Band’s Inset Is the Band’s, Not the Grid’s

In `0.3.3` the wide band applied its 2.5rem column inset through
`.kpress-content-with-toc .kpress-long-text`. That selector matches whether or not a TOC
was rendered, because `.kpress-content-with-toc` is on the layout wrapper always.

`0.3.4` rewrote the inset as `--kpress-column-inset` and, in the same move, gated the
wide-band value on the rail conditions — the same `:has()` pair that selects the
two-column grid. The grid genuinely needs a rail.
The inset does not: it applies to a single column too.
So a wide document with no TOC and no reserved rail silently kept the single-column
band’s 4rem.

The reading measure was never wrong.
The caps derive from the inset, so the text still landed at exactly the measure in both
cases — which is why the `0.3.4` browser tests, all of which reserve a rail, did not
catch it. What changed was the card’s inner padding, and with it the width of the card
around the text:

| Wide document | 0.3.3 | 0.3.4 | 0.3.5 |
| --- | --- | --- | --- |
| with a TOC or reserved rail | 2.5rem | 2.5rem | 2.5rem |
| without one | 2.5rem | 4rem | 2.5rem |

An embedding host is what notices.
`0.3.4` documents the wide content track as `measure + 2 × 2.5rem`, and a host that
sizes its own panels to that number to line them up with the document — a README shown
inside a folder summary, rendered with `include_toc="off"` — found the document inside
those panels no longer matching them.

The inset is now unconditional across the wide band, as it was in `0.3.3`.

## What Changes for You

If you render wide documents without a table of contents, their content card returns to
the `0.3.3` inner padding.
If you always render one, or always reserve the rail, nothing changes at all.

Hosts that adopted `0.3.4` and compensated for the 4rem should drop the compensation.

## Verification

The complete Python and JavaScript quality gates, locked-graph dependency audits,
distribution inspection, clean-room wheel install, and the Python 3.12–3.14 CI matrix
run before publication.

The gap `0.3.4` left was a test-coverage gap as much as a CSS one: every reading-measure
probe reserved a rail, so the un-railed path was never rendered.
`tests/test_playwright_reading_measure.py` now renders both, and asserts in Chromium
that the wide band’s inset is identical with and without a TOC, and that a TOC-less
document still reads at the measure in every band.
Both were confirmed to fail against the `0.3.4` rule before the fix landed.

The exact PyPI artifact is verified separately after trusted publication.
