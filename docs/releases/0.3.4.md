# KPress 0.3.4

KPress `0.3.4` is a compatible bug-fix release for the `0.3` declarative-embedding line.
It repairs `--kpress-measure`, the pinned public token that sets how wide documents
read. The token did not work, and the same token meant two different widths depending on
how wide the pane was.

The public API grows but does not break: two layout tokens join the fragment contract
and nothing is removed or renamed.
Documents do re-flow, which is the point of the release and is described below.

## The Reading Measure Now Controls the Reading Column

`--kpress-measure` is pinned in `PUBLIC_FRAGMENT_CSS_VARIABLES`, and
[the design reference](../kpress-design.md) tells an embedding host to set it on the
`.kpress` scope. Nothing that sized the reading column read it.

Measured in Chromium against a plain fragment, with a host override of `64rem` on
`.kpress` — a request for 16rem more text:

| Pane | Band | Default | With the override | Effect |
| --- | --- | --- | --- | --- |
| 56rem | single column | 38rem | 40rem | +2rem |
| 81rem | wide | 48rem | 48rem | none |
| 100rem | wide | 48rem | 48rem | none |

The 2rem that did move was `.kpress-doc`’s own allowance leaking through; the column
behind it then met a hard-coded literal and stopped.

Three elements bound the column, and each counted a different part of the padding
between itself and the text:

| Element | Cap before | Counted |
| --- | --- | --- |
| `.kpress-doc` | measure + 2rem | one gutter pair, no inset |
| `.kpress-doc-layout` | measure | no padding at all |
| `.kpress-long-text` | `min(100%, 48rem)` | a literal duplicating the measure |

The wide band added a fixed `grid-template-columns: 15rem 53rem` on top.

So one token meant **the text** where the grid track added the inset back, and **the
text plus two insets** everywhere else.
That is a 10rem step in reading width across the 75rem band boundary, and it is why
setting the public token moved the article while leaving the text where it was.

All four now derive from the token.
`--kpress-column-inset` is the inline padding inside the column and
`--kpress-doc-gutter` is the page margin outside it; the bands reset those two on
`.kpress-doc`, and each cap adds back exactly the padding between it and the text:

| Element | Cap |
| --- | --- |
| `.kpress-doc` | measure + 2× inset + 2× gutter |
| `.kpress-doc-layout` | measure + 2× inset |
| `.kpress-long-text` | measure + 2× inset, padded by the inset |

The text lands at the measure in every band.

The band conditions stay literal lengths, because a container query cannot read `var()`.
They are now the only part of the system that does not follow the measure: changing it
changes how wide documents read, not where the bands switch.
The wide band’s content track carries a `min()` against the pane so a host measure
larger than that floor assumed degrades instead of overflowing.

## The Measure Now Tracks the Type

The default moves from `48rem` to `calc(var(--kpress-font-size-base) * 45)`.

A root-relative measure holds its pixels while the type changes underneath it, so a host
that pins `--kpress-host-font-size-base` gets a line length it did not choose.
Deriving from the base holds the characters per line instead.
For a standalone page the two are identical — the base defaults to `1rem` — so this is
visible only to embedders.

Write a host measure as `calc(base × N)` rather than `N em`. An `em` inside a custom
property resolves at each *consuming* element, and three elements with different font
sizes read this one, so `45em` would silently mean three lengths.

## What Changes for You

Reading width changes on every document.
At the default base both bands land at 45rem of text, where they were 48rem in the wide
band and 38rem in the single-column one.
In PT Serif that is about 104 characters either way, against about 111 and 88 before.

This is a rendering change rather than a repair of something visibly broken, so it is
worth looking at a page you publish in both a wide and a narrow pane.
A host that wants a different width now has a token that works:

```css
.kpress {
  --kpress-measure: calc(var(--kpress-font-size-base) * 52);
}
```

### Characters Per Line

The measure is a length, not a character count, because the conversion depends on the
face. Measured over 507 characters of representative English prose, the average glyph
advance is 0.4335 em per character for PT Serif and 0.4039 for Source Sans 3, so the
default reads about 104 and 111 characters.
Eight common proportional text faces span 0.392–0.434, which puts `45em` in the 104–115
character range for any of them.

This is the average advance, not the CSS `ch` unit.
`ch` is the advance of “0”, overstates a proportional face by roughly 23%, and its
relation to the average varies more across faces (0.66–1.0) than the average does.

KPress ships no per-face constants, because `--kpress-host-font-prose` lets a host swap
the face and invalidate them.
A host knows its own pinned face and can convert; the ratios above are recorded in the
design reference for that purpose.

## Compatibility

No name, CSS class, CSS variable, template variable, or data attribute was removed or
renamed. `--kpress-column-inset` and `--kpress-doc-gutter` join `PUBLIC_CSS_VARIABLES`
and `PUBLIC_FRAGMENT_CSS_VARIABLES`.

The `, 76ch` fallbacks inside the two `var(--kpress-measure, 76ch)` calls are gone.
The caps now read three tokens, and a fallback on one of them would compute a quietly
wrong width instead of failing visibly.
`style-tokens.css` is a required asset, so the tokens are always defined and the
fallback was already unreachable.

A host that overrode `.kpress-long-text`’s `max-width` or the wide band’s
`grid-template-columns` to work around the old behavior should remove that override:
those rules now follow the measure, and a host copy of the old literals will fight them.

## Verification

The complete Python and JavaScript quality gates, locked-graph dependency audits,
distribution inspection, clean-room wheel install, and the Python 3.12–3.14 CI matrix
run before publication.

The claims here are container-query and cascade behavior that browserless DOM emulation
does not evaluate, so they are pinned by a real browser rather than by unit tests.
`tests/test_playwright_reading_measure.py` asserts three things in Chromium, each in
both a wide and a single-column pane: the reading width is the same in every band, a
host override of the token reaches the text, and the measure follows a pinned type base.
Panes are sized inside a wider window throughout, so a viewport-keyed rule fails rather
than passing by coincidence.

The visual-parity contract now pins the derivation rather than a literal track width.
A literal there is what let the track drift out of step with the token in the first
place.

The fix was also verified downstream before release, by building the branch as a wheel,
installing it into an embedding host, and confirming in the browser that the band step
is gone.

The exact PyPI artifact is verified separately after trusted publication.
