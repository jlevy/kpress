# KPress 0.3.10

Task-list boxes drawn by KPress itself, an `<input>` kept in `sanitized` mode only as a
disabled checkbox, and fixes to what `sanitized` mode lets a document do to its host
page.

## Task Lists

- KPress draws the box of a task list item (`- [ ]`, `- [x]`) from its own MarkdownIt
  token, `kpress_task_checkbox`, with the state in `meta["checked"]` (`True` when
  ticked) and the source marker in `markup`. It replaces the `tasklists` plugin from
  `mdit-py-plugins`, which wrote the box as an `html_inline` token holding raw `<input>`
  HTML, so a consumer of the token stream had to match that HTML to find the box and its
  state.
- The token carries the box’s attributes (`class`, `checked` when ticked, `disabled`,
  `type`), so any MarkdownIt renderer, the stock one included, writes the same disabled
  checkbox.
- The rendered HTML is unchanged in both trust modes: the same `<input>`, the
  `kpress-task task-list-item` item and the `contains-task-list` list.
  Those classes are now set on the item and list tokens instead of being added to the
  rendered HTML afterwards.
  A raw `<li class="task-list-item">` the author writes no longer gains `kpress-task`.
- The item and list open tokens list the classes KPress appended in
  `meta["kpress_classes"]` (`kpress-task` and `task-list-item` on the item,
  `contains-task-list` on the list, less any the author already gave), so a consumer of
  the token stream can tell them from classes given by attribute syntax.
- The box keeps its look, and its item has no bullet, in a host that strips KPress’s
  classes and keeps only `<input type="checkbox" disabled>`: the styles key on the box
  being the first element of its item, or of the item’s first paragraph, as well as on
  the classes. Where the classes are present nothing changes.
  An item whose first element is a checkbox after some words also loses its bullet,
  since CSS cannot see the words.
  Only a bulleted item loses its marker that way: an ordered item, a footnote among
  them, keeps its number, so without the classes an ordered task list shows the number
  beside the box.
- A task item in a footnote has `kpress-task` in `DocumentTree.footnotes` too, as in the
  body. Only the body had it before.
- An item whose marker is followed by a tab or a form feed gets its box.
  The plugin marked it as a task but drew no box.
- A marker that only spaces, tabs and a line ending follow (`- [ ]`, then the item goes
  on on the next line) is text, as on GitHub.
  The plugin marked `- [x]` followed by a line ending as a task with no box, and drew a
  box for `- [ ]` followed by a space and a line ending.
- Any whitespace character between the brackets other than a line ending, a tab for
  example, is an open box, as on GitHub.
  Only a space was before.
  GitHub shows a vertical tab as U+FFFD, so there a vertical tab between the brackets is
  text; KPress follows GFM and draws the box.
- A class given to the list by attribute syntax (`{.checklist}` above it) is kept.
  The plugin replaced it with `contains-task-list`.
- When the document defines `[x]` as a link, `- [x] Done` shows the link and no box, as
  on GitHub. The plugin drew the box and kept the link.

## Sanitized Inputs

- In `sanitized` mode an `<input>` whose `type` is not `checkbox` is removed, a missing
  `type` included, since that is a text field.
  `type` is matched without regard to ASCII case or surrounding whitespace.
  A checkbox keeps only `checked` and the class `task-list-item-checkbox`, alone, and is
  always `type="checkbox"` and `disabled`. The task-list box passes unchanged.
  Before, a raw `<input>` kept its `type` and the attributes any element could carry,
  such as `form`, `src`, `id`, `class`, and `title`, and lost the rest, such as `name`,
  `value`, `placeholder`, `formaction`, and `on*`, so a text or password field, a submit
  button tied to a form on the host page by `form`, or `type="image"` loading a remote
  image reached the reader.
  A checkbox cannot take another KPress class.
- Every input is written in the attribute order of KPress’s own box, with `checked` as
  `checked="checked"`, so the same input always sanitizes to the same bytes and a
  hand-written box to KPress’s own.
- Each attribute removed or set is reported as an `html_sanitized_attribute` diagnostic,
  for example `Set attribute 'type' to 'checkbox' on <input>.` An input that is not a
  checkbox, or does not survive parsing, such as one inside `<svg>`, is reported as a
  removed tag, and one inside `<noscript>`, which becomes text, is not reported as an
  input. An input change the audit cannot explain gets the catch-all `html_sanitized`
  even beside other diagnostics, and so does one where the inputs the audit expects kept
  are not those kept, in order and attributes.

## Sanitized Mode

These fix problems older than this release.

- A `<button>` is always `type="button"`, and no element keeps `form`, so a document
  cannot submit or reset a form on the host page.
  `<button form="host-form">`, a bare `<button>` inside a form on the host page, and
  `<button type="reset" form="host-form">` did so in Chromium.
  KPress’s own video button is already `type="button"` and is unchanged.
  `form` can no longer be declared in `format.html.extra_attributes`.
- Each raw `<button>` without `type="button"` now gets an `html_sanitized_attribute`
  warning, `Set attribute 'type' to 'button' on <button>.`, and one that does not
  survive parsing, such as one inside `<svg>`, is reported as a removed tag.
- `<link>` is removed.
  `<link rel="stylesheet" href="…">` loaded and applied a remote stylesheet.
- An `svg` fence drops any `<input>`.
- Each note in `DocumentTree.footnotes` is sanitized as the body is.
  A note’s HTML was not sanitized, so its `<script>` survived there while the body was
  clean. A plain note changes only in nh3’s spelling, as the body does: a literal quote
  is `"`, not `&quot;`, a no-break space is `&nbsp;`, and `&#x0003C;` in MathML is
  `&lt;`.
- HTML a host passes as `DocumentInput.body_html` is sanitized in `sanitized` mode, as
  rendered Markdown is.
  It was emitted as written in every mode.
- The diagnostics read `<![CDATA[` as html5ever, and a browser, do: outside SVG and
  MathML it ends at its first `>`, so what sanitizing changes in the markup after that
  is reported. It was sanitized without a diagnostic.
  In SVG and MathML, `<style>` and the other elements whose content is text in HTML are
  ordinary elements, so what sanitizing removes inside them is reported too.
